## Findings, ranked

**1. SVG alpha is composited as straight while the source is premultiplied — every semi-transparent pixel comes out too dark.** `core/src/source.rs`, `Source::open`'s SVG branch. tiny-skia's `Pixmap::take()` returns **premultiplied** RGBA8 (resvg renders with `SourceOver` into it), and svg.rs's own comment ("Do not premultiply or convert") confirms the assumption is straight. The formula used, `(c*a + 255*(255-a) + 127)/255`, is the straight-alpha over-white equation, so `a` is applied twice. Opaque (`a=255`) and fully transparent (`a=0`) are correct, which is why the test (`test_rasterize_rectangle_and_color`, an opaque rect) passes. A white shape at 50% alpha composites to 191 instead of 255; a red edge pixel `(255,0,0,128)` gives 191 instead of 255 in the red channel — the classic dark halo along every anti-aliased edge, i.e. every rasterized logo. Correct form for premultiplied input is `out = c + (255 - a)` (or de-multiply through `Pixmap::pixels()`/`to_color`). This is silent output corruption and outranks everything else here.

**2. Quality and Balanced still refuse every SVG, because `search` keeps its own never-grow check that the new exemption does not cover.** `lib.rs`, `search()`'s final `if chosen.bytes >= original_bytes` and `search_by_proxy`'s `if full_data.len() >= original_bytes`, both called with `bytes.len()` — the SVG's byte length. A 398-byte drawing rasterizing to 13 KB (your own number) hits `NoSmallerResult { best_bytes: 13000, original_bytes: 398 }`: "target is only reachable at 13000 bytes, larger than the original 398". So change #2 achieves its stated purpose only in Fast mode; `squint drawing.svg --mode quality` and `--mode balanced` both fail on the exact case the exemption was written for, and a full-resolution HEIC is now produced in Fast but refused in Quality. Decide the conversion policy once, in `optimize`, and have `search`/`search_by_proxy` take it as a parameter (or drop their copies of the check and let `optimize` be the only judge). Otherwise the shipped rule is "conversions are exempt only where nobody searches".

**3. `strip_gif` validates declared sizes, not structure — a wrong LCT flag desyncs the walk and a `0x3B` inside LZW payload is then accepted as the trailer.** Answering Q1: the walk handles a `0x3B` inside LZW data or a colour table *structurally* only as long as the sizes it reads are the real ones — the LZW payload is skipped by declared sub-block length, the tables by computed length, so a `0x3B` there is never examined. Everything rests on those declarations agreeing with the bytes. Flip one bit in the image descriptor's packed field (LCT flag set on a file with no local table, or the size bits changed): `pos += 10 + lct_len` lands inside the LZW stream, the next byte is read as a sub-block length, and the walk resynchronizes on whatever LOOKS like a block. If any byte in the picture data is `0x3B`, `trailer_reached` is set and `Some(truncated)` is returned — and Strip writes that over the original GIF, which is the 2026-08-19 failure with a different container. The corruption is self-consistent (the emitted span ends on the byte the walk believed was a `0x00` terminator), so a tolerant decoder may still open the partial picture and no complaint is raised. The `if pos > bytes.len() || bytes[pos - 1] != 0x00` check is close to dead weight: when the loop breaks on a real sub-block terminator, `pos-1` is `0x00` by construction, so the check can only fire on the EOF exit, which `trailer_reached` already catches. What is missing is a check that the walk's size arithmetic is consistent — e.g. require the block to end where the file says the picture ends, or re-validate the emitted span by walking it again before returning.

**4. `rasterize` bounds only the canvas, and the default `href` resolver will read local files.** Answering Q4: `MAX_PIXELS` is checked on the computed target, before `Pixmap::new` — correct, and it does what it says for the declared size. It bounds nothing else. `<filter>` regions, chained groups, `patternUnits` tiling and deeply nested `<use>` are expanded or rasterized inside usvg/tiny-skia with no resource limit configured (`usvg::Options` is `default()` except for `fontdb`); confirming whether usvg caps `<use>` recursion depth or filter-region area needs the crate source, which I did not read — I would not assert it does. What I can assert: `usvg::Options::default()` leaves `resources_dir` at the process working directory and leaves the default `ImageHrefResolver` in place, which resolves non-`data:` `href`s (including `file:` and relative paths) by reading from disk. So `<image href="../../etc/passwd">` is a file read this program performs and then encodes into a JPEG it writes. Set the resolver to a data-URL-only one (or refuse external hrefs) before shipping rasterization; an optimizer has no reason to touch the filesystem for pixels it was not given. Billion-laughs is likely closed already (roxmltree does not expand DTD entities), but that is a crate property, not a decision made here.

**5. The CLI's PNG branch never learned about `balanced`, so it measures Fast for PNGs while the app gets Thorough + a target.** `core/src/main.rs`: `let measure = mode == "quality"; let effort = if mode == "quality" { Thorough } else { Quick };` — `--mode balanced` on a PNG falls into the Quick, unmeasured path, whereas `optimize()` maps Balanced to `Effort::Thorough` with `Some(target)`. That is precisely the harness/application divergence the comment above the `"fast" | "quality" | "balanced"` match says was already fixed once. The `--against` and strip branches are fine.

**6. Answering Q2.** The keep-list is right in kind but the match is too generous and too narrow at once. Too generous: the decision is all-or-nothing on an 11-byte prefix of the first sub-block, so any `0xFF` application extension whose identifier happens to be `NETSCAPE2.0` is preserved in full — including every subsequent sub-block, which is a free 60 KB carrier for metadata smuggled behind the identifier. A hostile file keeps whatever it likes that way. Too narrow: `ANIMEXTS1.0` is the other identifier used for the animation loop count (Netscape lineage, still emitted in the wild); a GIF carrying it loses its loop and is treated as a normal extension. GCE is the right thing to keep (delay and transparency index are rendering, not metadata); Plain Text (`0x01`) is dropped by the same exclusion, which changes what the picture looks like, though the block is effectively extinct. A safer keep is GCE plus, for `NETSCAPE2.0`/`ANIMEXTS1.0`, only the loop sub-block (`0x03 0x01 lo hi`) re-emitted, not the whole raw span.

**7. Answering Q7 — the corpus breaks on both new formats, in different places.** `corpus-run.py` (`resembles`) scores the output by running `squint <ref.png> --against <out>`, which goes through `Source::open` → `Image::decode_capped` → the `image` crate built with `features = ["png","jpeg"]`. A GIF output cannot be decoded there, so `--against` exits non-zero, `resembles` returns `None`, and `judge` reports "output could not be scored against the seed" — a false DANGEROUS for every GIF `strip` run, control family included. For SVG the break is `expected_dimensions`, which derives the expected output size from the **seed PNG**, not from the variant: vector output sized by the document's own width/height matches only if the generator emits SVGs whose intrinsic size equals the seed raster's exactly. `email_extension` is fine (SVG → `.jpg`, matching the engine). Also worth stating plainly: `balanced` is in no `MODES` list, so the new mode ships with zero corpus coverage — and the corpus's judgements (size, magic, resemblance) would not exercise the proxy path even if it were added.

**8. Minor.** `core/src/main.rs`: the `JPEG_SCORE_CEILING` error string lost its line-continuation backslash and now carries a run of spaces mid-sentence ("…about 91;                      the search cannot converge"). `Error::NoSmallerResult`'s doc comment still reads "An optimizer must never grow a file", now untrue for converted sources. In Balanced, `SearchResult.chosen.bytes` is the full-size length while `probes` carry proxy byte counts and `r.score` is `None`, so no probe is ever marked `<- chosen` and the printed table is in different units from the line under it. `is_svg` only looks 1 KiB in and terminates DOCTYPEs at the first `>` (a system identifier containing `>` truncates it), so a valid drawing with a long declaration preamble falls through to `Error::Decode`; harmless, but it makes the "read" half of the format decision depend on a window.

**9. Answering Q6.** `fontdb`'s load is one-off and mmap-backed, so the cost is real but bounded and paid once — 0.68 s first call, measured. It does walk the user's font directories, which is the only filesystem work on the SVG path that cannot be attributed to a `href`; `fontdb::Database::load_fonts_dir` over the system directories, with the per-user directory skipped, is the bounded version if that matters. `resvg`'s default features pull `gif` and `image-webp` (via its own decoders) which rasterize `<image>` payloads you would be refusing anyway once the resolver is restricted; `usvg`'s default features cannot be trimmed much without losing text (`harfrust`/`skrifa`/`fontdb` are the text path itself).

**10. Answering Q3 and Q5.** `converted_from.is_some()` is a proxy for a caller's behaviour, which the engine cannot see, and it is not sound on its own: `lib.rs` is also reached through the C API (`squint_optimize` returns `converted` as a flag the caller may ignore) and through `main.rs --out`, which writes wherever it is told with no comparison against the input path. The only guard that actually holds is `JobQueue.swift`'s `if result.converted && destination == url`, which is sound — it compares paths, not extensions, so an SVG named `photo.jpg` is still refused. The consequence is that the engine's rule now depends on one Swift caller for its correctness; the exemption should be an explicit parameter (or applied in the caller), not inferred from a field. On white: compositing onto white is a defensible default for a drawing with a transparent background, but it is a choice the engine makes silently, and for light-on-transparent art the result is a blank image. The cheaper honest answer is the same one HEIC already gets — report the conversion, and let the caller say what the backdrop is, defaulting to white only if nothing is said. Either way the arithmetic in finding 1 has to be fixed first; picking a colour correctly does not help if the blend is wrong.
