## 1. The RIFF walk: no panic, no overflow — but it accepts garbage as a file

`walk()` is clean on the classic hazards: `at + 8 > bytes.len()` guards every header read, `at + 8` can't overflow (caller is ≤ `usize` meaning), the payload range is bounds-checked before it's sliced, `is_webp` runs first so `bytes.len() - 8` can't underflow, and there is no allocation sized from a file field. `walk()` lands exactly on `bytes.len()` or returns `None`. That part is right.

**Finding 1a (confirmed, highest severity).** The exactness rule is enforced, but that is all that is enforced. Nothing checks that each chunk *looks* like a WebP chunk, and *payload content is never validated*. The walk hands every chunk to `f` before the caller can object — `strip_webp`'s `has_picture` test only matches the four-byte FourCC, and `is_animated` likewise. So this is accepted as a valid, stripped WebP:

```
RIFF <n> WEBP  [wicz <k> <k bytes>]  [wicz <m> <m bytes>]  ...landing exactly on EOF
```
with one chunk whose id is `VP8 ` and payload `[0x00]`. `strip_webp` returns `Some`, `wiped == bytes.len() - 12` because the garbage chunks are "metadata", and `lib.rs` returns `Ok`. Downstream the `image` crate reaches `image-webp`'s *unchecked* `WebPDecoder::new` (I'm fairly confident it is unchecked for WebP in `image` 0.25; that one piece is recall, not read), which pushes the 1-byte payload into `reassemble_image` for a lossy chunk and panics on slicing. That is a panic on arbitrary user input from the Finder context menu — the exact scenario in your question. Your malformed-corpus pass wouldn't find it because it fuzzes JPEG segment lengths and truncation, not the WebP chain.

Two fixes, cheap: require a picture chunk to have a payload minimum (`VP8 ` ≥ 10 has no start code to check, so a length floor; `VP8L` ≥ 5 and check `payload[0] == 0x2F`; `VP8X` ≥ 10 and check the two reserved bits are zero), and have `strip_webp` return `None` when the chunk it kept as picture doesn't validate. Rejecting beats forwarding.

**Finding 1b (confirmed).** A WebP containing only `ICCP` and `EXIF` (no picture chunk) and one containing a picture chunk with a *zero-length* payload behave differently and both wrong. The first is caught — `has_picture` stays false, `None`. The second returns `Some` with `wiped > 0`, so the lib.rs branch never sees `wiped == 0` and happily emits a "stripped" WebP with a blank picture, which `Source::open` then decodes to an image of nothing through an `unwrap_or`-style fallback rather than reporting the blank. A payload-length floor fixes this too.

**Finding 1c (suspected).** Every `span` is arithmetic on an unvalidated `u32`; with ≥ 2 GB of chunk lengths the walk can loop ~2^31 times calling `f`. `strip_webp`'s cost is O(payload bytes copied) because it counts payloads rather than `span`, so the pathological case is bounded on memory but `is_animated`/`icc_profile` would spin for a very long time. Only reachable if you first `mmap` the file — worth knowing, not worth fixing on its own. I did not measure it.

## 2. The keep-list: correct, with one known gap

`ALPH` is right to stay: in the WebP container spec `ALPH` is losslessly compressed (or raw) alpha and `VP8L` in-place alpha handling uses `0x10000000`-class length conventions — removing it while keeping the extended header's alpha flag would hand decoders a block they can't parse. `ANIM`/`ANMF` staying is right, and that also means **`ANIM`/`ANMF` are missing from what a strip removes** — an animation's loop count and per-frame duration are not records of a pixel, but they are metadata a stripper can be argued either way about. Not a bug; flag it in the docs so it isn't discovered later.

The gap: **`VP8X`'s alpha flag (`0x10`) is never cleared even when `ALPH` is absent.** For a file with the animation flag set but no `ANIM` chunk, `is_animated` correctly sees nothing animated — the walk is deliberately independent of the flag — but the emitted file still announces animation and carries no `ANIM`. The same header/chain disagreement you fixed for the EXIF/XMP bits is left standing for `0x02` and `0x10`.

Also worth stating in the module doc: chunks whose *type byte is non-ASCII* are byte-compared and dropped by exclusion, which is correct and is the point of the design. Nothing in the standard container is being dropped by mistake.

## 3. `is_animated`: the idea is right, one asymmetry

Walking chunks is the better signal, as the doc argues. The problem is the asymmetry with `strip_webp`, which keeps `ANIM`/`ANMF`. So an `ANMF`-only file is a still with respect to `is_animated` (no `ANIM` — and a demuxer emits frames from the `ANMF` list while the animation *header* is what `ANIM` provides) but is picture with respect to the strip. Fix: treat "any kept chunk that is animation-like" as the refusal condition (`is_animated`, not the decoder's flag — that is still the sound choice, because a stale flag would refuse a multi-megapixel re-encode of a still), checked **once, in `Source::open`, before the strip branch**, rather than separately in the strip branch where the verdict can disagree. `image`'s `AnimationDecoder` for WebP is driven by `has_animation()`, which is what makes the ANIM-only file decodable and the ANMF-only file not; if `has_animation()` is true it emits every `ANMF` as a frame, and `Source::open` would take only the first — so under the current order, ANIM-only animation reaches the still path and every frame after the first is silently lost.

## 4. AVIF split: correct; one open question about `is_heif`

`compatible_brands` is sound — `bytes[16.min(end)..end]` cannot panic because `end ≥ 16` in both arms, `chunks_exact(4)` discards a ragged tail, and a size that doesn't fit the slice yields an empty iterator (their two tests assert exactly that). The `!is_avif(bytes)` conjunct in `is_heif` is necessary given `mif1` is in the HEIF brand list, and the mif1-leading case is handled and tested.

One real minor: `compatible_brands` reads through the declared `ftyp` size whenever that size fits the *slice*, without checking it against the box's own header — a file whose `ftyp` declares 1024 bytes swallows following boxes as "brands". The only brands that matter are `avif`/`avis`, and accepting a real still as AVIF purely because a later box happens to contain that FourCC is a bad-name bug, not a strip bug (the ISOBMFF walk is codec-agnostic). Bounding it to the actual `ftyp` box would fix it. **The thing I could not verify, and you should:** a HEIC whose `ftyp` compatible list includes `avif` — I believe some Apple HDR HEICs carry `avif` in the brand list, which would now route them down the AVIF path and label them AVIF everywhere including `converted_from`. I'd grep your own HEIC corpus for `avif` in the first 64 bytes before shipping.

## 5. `VP8X` flag clearing: the premise is wrong, and there is a corruption path

`VP8X` is *not* guaranteed to be the first chunk. The spec's bitexactness section requires `VP8X` to precede the bitstream chunk, which permits `ICCP` and `ALPH` before it — and this module's own doc comment says the chain is "the same as the original" and doesn't check order, so the assumption is the code's, not the format's. When `VP8X` isn't first, the block is skipped: no corruption, but a stale `0x08`/`0x04` flag left describing a file that no longer carries those chunks — the exact failure the block exists to prevent, just quieter.

**Finding 5a (confirmed, concrete corruption).** `out[20]` is guarded by `out.len() > 20`, not by "`VP8X` has a payload". Take `VP8X` with a declared length of 0 followed by a kept chunk: `out[12..16] == b"VP8X"` still holds, and `out[20]` is now the *first byte of the next chunk's FourCC* — you AND it with `!0x0C`, renaming the chunk. `VP8 ` (0x56) becomes `RP8 `; `ICCP` (0x49) becomes `ACCP`. With at least one dropped chunk `wiped > 0`, so `lib.rs` writes that file out and reports success; the picture chunk or the profile has been renamed and the output is not a WebP any decoder will take. Input to trigger: `RIFF`+`WEBP`, then `VP8X` len 0, then `EXIF`, then a `VP8 ` chunk. Bounding the clear to the chunk that the walk validated (`span == 18` for a 10-byte payload) and clearing it on the chunk you actually identified, rather than at a fixed absolute 20, removes the whole class.

## 6. Silent paths

- **The profile is read through the same torn chain.** `icc_profile` swallows the walk's `None` and returns `None`, which is indistinguishable from "this file carries no `ICCP`". A wide-gamut WebP cut short in transit therefore loses its profile and comes back untagged — flat, and reported as a success. That is the project's headline differentiator on a path that reports nothing. Have `Source::open` distinguish "no `ICCP` chunk" from "the chain didn't close"; the former is sRGB, the latter should be a refusal.
- **The stripped WebP never passes the never-grow guard.** The early `return Ok(...)` in the strip branch bypasses `Source::open` entirely. It's safe here because a rebuild is monotone (only dropped chunks leave, and `wiped > 0` is required), so it can't grow — but it is worth a comment, because that invariant is what makes the bypass legitimate and nothing asserts it.
- **`is_animated`'s `let _ =` is documented as safe for both callers, and it isn't.** The doc says a chain that doesn't close "yields no chunks, which reads as a still, and the file then reaches a decoder that will refuse it". `strip_webp` does refuse. The still path does not: `image-webp` (via `WebPDecoder::new`, unchecked) would decode frame 1 of the truncated animation and re-encode it, and the remaining frames are gone with no error. Reordering per §3 fixes this too, since the refusal in `Source::open` would be the animation check rather than the decode.
- Everything else is loud: `Error::Decode` for a WebP that won't strip, `Error::NoSmallerResult` when `wiped == 0`, and the AVIF test asserts the container name reaches the message, not just the struct.

**Outside the six, one paragraph.** `Source::open` sets `orientation: 1` for WebP and asserts that a file carrying EXIF "has already had it applied by whatever wrote it". That is not true of `cwebp -metadata all`, which copies the EXIF payload verbatim, orientation tag included, without rotating the pixels. A WebP made that way from a portrait JPEG is decoded unrotated and written as a JPEG with no tag — sideways, silently, in the convert tier. Either read the orientation out of the `EXIF` chunk and bake it like the JPEG path does (you already have `extract_orientation`), or state the exclusion explicitly in the module doc so it is a known limit rather than an assumption.

The "already verified" list holds up: I found nothing in it that is wrong, and the strip/rebuild byte counts and the `0x08 → 0x00` flag observation are consistent with the code as written. What the list doesn't cover is hostile input to the still path — the corpus pass exercises JPEG only, so the walk's acceptance of arbitrary bytes and the `out[20]` corruption are both outside what 67 green tests and 4 real files would have shown.
